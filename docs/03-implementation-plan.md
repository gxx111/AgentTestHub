## 1. 前提与假设

### 1.1 团队假设

按 **5 名全职 + 0.5 设计 + 1 名兼职产品/评测负责人** 规划：

| 角色 | 人数 | 职责 |
|---|---:|---|
| 后端/平台 | 2 | 领域、API、DB、队列、鉴权 |
| 执行/沙盒 | 1 | Runner、Docker、MCP、模拟器 |
| 评测/数据 | 1 | Judge、校准、统计、场景包 |
| 前端 | 1 | 控制台、报告、Trace 查看器 |
| 设计 | 0.5 | 设计系统、关键流程 |
| 产品/评测负责人 | 1（兼职） | 设计伙伴、需求、验收 |

如果只有 2–3 人，时间线乘 1.8–2.5；如果 8 人以上，可并行 Phase 1/2 的部分工作。

### 1.2 技术前提

- 本地 Docker 可用；CI 有 Docker。
- 至少一个可用模型网关（OpenAI 兼容/LiteLLM）。
- 设计伙伴能提供真实场景与人工标签（至少 100 条）。
- 允许在 Phase 0 做一次数据迁移与 API 破坏性调整（beta 阶段）。

### 1.3 交付原则

1. **先可信，再丰富**：P0 未完成前，不新增可视化大屏。
2. **每个里程碑都有可演示的端到端结果**，不是"底层完成"。
3. **设计伙伴每周可见**：demo + 真实用例 + 反馈闭环。
4. **默认私有化可部署**：所有功能不能依赖某个 SaaS。
5. **删除优于兼容**：beta 阶段允许删除错误抽象，不做无限兼容。

## 2. 工作流（Workstreams）

| 流 | 代号 | 范围 | 负责人 |
|---|---|---|---|
| 可信评测 | A | Judge、Rubric、评分、校准、统计 | 评测/数据 |
| 执行环境 | B | Runner、沙盒、MCP、双控模拟、红队 | 执行/沙盒 |
| 平台工程 | C | DB、队列、鉴权、租户、审计、部署 | 后端/平台 |
| 产品与 CI | D | SDK、CLI、GitHub Action、门禁、报告 | 后端/平台 + 产品 |
| 前端体验 | E | 控制台、实验对比、Trace、标注、报告 | 前端 + 设计 |
| 质量与安全 | F | 测试、黄金集、压测、安全、合规 | 全员 |

### 2.1 依赖关系

```text
A (可信评测) ──┐
B (执行环境) ──┼──> D (CI/门禁) ──> 设计伙伴试点
C (平台工程) ──┘          │
E (前端) ─────────────────┘
F (质量/安全) 贯穿所有阶段
```

- A 和 B 是差异化核心，必须最早启动。
- C 可以先做最小可用（Postgres + 队列 + 鉴权），不要过度设计。
- D 依赖 A/B/C 的稳定接口，但在 Phase 0 就可以做 CLI 骨架。
- E 跟随 API，不提前造页面。

## 3. 里程碑

### M0 · 真相与基线（第 1–2 周）

**目标**：让项目"说的和做的一致"，建立可信基线。

交付：
- 删除旧设计文档，统一到 `docs/`。
- README 重写，能力矩阵 + 限制清单。
- 现有 44 个测试全绿；补前端 build/typecheck。
- 记录当前真实评测基线（复用 validation 报告，修正数字不一致）。
- 建立 issue/roadmap 看板，按 P0/P1/P2 排序。

退出标准：
- 任何对外声明都能指向代码/测试/报告。
- CI 包含 Python + Web + 文档链接检查。

### M1 · 可信评测核心（第 3–6 周）

**目标**：让"通过/失败"可以被相信。

交付：
- 确定性 Evaluator：状态差分、工具 Schema/AST、SQL 安全（sqlglot）、策略、PII。
- LLM Judge 重写：证据校验、UNKNOWN、多模型/多票、成本上限。
- 评分契约：weight/severity/unknown 策略；删除 0/0.5/1。
- 修复安全否决 bug；实现真正的仲裁或改名为"仲裁"。
- 校准集 100–200 条；输出 Kappa/混淆矩阵/false pass。
- 黄金集测试进 CI。
- 任务队列 + 取消 + 超时；SSE 从 Redis 读。

退出标准：
- Kappa ≥ 0.7；已知坏用例 false pass < 5%。
- 同一配置重复运行，确定性检查 100% 一致。
- 安全 fatal 在任何路径都不能被推翻。

### M2 · 仿真 MVP（第 7–16 周）

**目标**：从"聊天评测"升级为"业务世界评测"。

交付：
- Docker 沙盒：非 root、只读 rootfs、网络拒绝、资源配额、快照/回滚。
- SQLite/Postgres 环境：真实主键、负向断言、允许变更集。
- MCP 真实客户端/代理：tools/list、tools/call、故障注入。
- 双控用户模拟器：用户有工具、隐藏目标、策略约束、目标覆盖。
- 红队库：提示注入、工具误用、数据外泄、权限绕过、MCP 投毒。
- 轨迹指标：工具选择/参数、计划遵循、步骤效率、状态差分、成本/延迟。
- 2–3 个垂直场景包（退款/审批/工单）。

退出标准：
- 能在 Docker 中跑通至少 2 个真实业务场景。
- 双控模拟器能独立完成"上传凭证/查询状态"等动作。
- 同一 seed 下故障注入可复现。

### M3 · CI 门禁与设计伙伴（第 17–24 周）

**目标**：让评测进入发布流程，拿到真实反馈。

交付：
- Python SDK + pytest 插件 + `ath` CLI。
- GitHub Action：PR 评论、退出码、baseline 对比。
- OTel 导出（GenAI 语义约定）+ 3 个框架适配器（LangGraph、CrewAI、OpenAI Agents SDK 或 smolagents）。
- 实验对比 UI：通过率、CI、fatal、成本/延迟、flaky。
- 标注队列 + 校准仪表盘。
- 报告：自包含 HTML + manifest + 签名（可选）。

退出标准：
- 3 个设计伙伴接入；至少 1 个在真实 PR 中使用了门禁。
- 一次完整实验（≥50 用例 × 5 重复）在 30 分钟内完成。
- 设计伙伴能独立创建数据集/实验/门禁，不需要工程师陪同。

### M4 · 生产闭环（第 25–36 周）

**目标**：从"发布前"扩展到"生产中发现 → 回流"。

交付：
- OTLP 摄入 + Session/Thread 视图。
- 在线评估：采样、异步 evaluator、告警、漂移。
- Trace → 标注 → 数据集飞轮。
- Postgres + Redis + S3 + Worker 自动扩缩；租户隔离。
- SSO/OIDC、RBAC、审计日志、配额。
- 私有化 Helm/Compose 部署包；air-gapped 文档。

退出标准：
- 10 个付费/试点团队；30% 实验来自 CI。
- 在线评估覆盖至少 1 个生产场景。
- 通过一次外部安全评审（或渗透测试）。

### M5 · 企业与规模化（第 37–52 周）

**目标**：可卖、可扩展、可审计。

交付：
- SOC2/ISO27001 准备；等保/信创适配。
- 场景市场/私有模板；团队协作与权限细化。
- 成本/配额/计费；SLA；支持流程。
- 公开"评测的评测"报告；案例研究。
- 生态合作与标准贡献（OTel/MCP/A2A）。

退出标准：
- 企业版可独立部署、可审计、可计费。
- 至少 3 个可公开引用的客户案例（经授权）。
- 品类认知：在目标客群中被视为"Agent 发布门禁"的首选之一。

## 5. 迁移与切换

### 5.1 阶段

1. **并行**：新引擎与旧 Runner 同时存在；新引擎通过适配器跑旧 YAML。
2. **只读迁移**：旧 SQLite 实验迁移为只读历史；新实验写 Postgres。
3. **切换**：Web 默认走新 API；旧 API 保留一个 minor 版本。
4. **删除**：旧 Runner/Judge/模拟 Docker 实现删除；文档同步。

### 5.2 数据迁移

- 导出 SQLite：workspaces/users/agents/datasets/cases/experiments/runs。
- 映射到新 schema；无法映射的字段进 `legacy_metadata`。
- 校验：行数、关键字段哈希、抽样对比。
- 回滚：保留 SQLite 备份 30 天。

### 5.3 兼容策略

- 旧 YAML 格式：提供 `LegacyYamlLoader`，转换为新 `Case`/`Rubric`。
- 旧 API：`/api/v1/evaluations/run` 保留为兼容端点，内部转新实验。
- 旧报告：保留 JSON 读取；新报告格式向前兼容。

## 6. 设计伙伴计划

### 6.1 选择标准

- 有 1–2 个生产/准生产 Agent，愿意提供真实用例与失败样本。
- 有 QA/平台团队，能每周投入 2–4 小时。
- 愿意签署数据使用/保密协议，允许匿名案例。
- 不在同一垂直领域选超过 2 家，避免场景冲突。

### 6.2 节奏

- 每周一次 45 分钟：上周结果、本周目标、阻塞。
- 每两周一次联合评审：场景包、评分、报告。
- 每月一次业务复盘：是否拦住真实问题、节省多少人工、门禁是否可用。

### 6.3 交换

- 伙伴获得：免费/折扣使用、场景包定制、优先支持、联合案例（可选署名）。
- 我们获得：真实数据、人工标签、失败样本、产品反馈、案例。

### 6.4 退出

- 连续 3 周无使用/无反馈 → 降级为普通试用。
- 数据质量不达标（无标签/无真实用例）→ 不纳入校准集。

## 7. 运维与 SLO

### 7.1 环境

| 环境 | 用途 | 数据 |
|---|---|---|
| dev | 本地开发 | 假数据/SQLite |
| staging | 集成/演示 | 脱敏数据 |
| prod | 客户/设计伙伴 | 真实数据，隔离 |

### 7.2 监控

- 平台自身用 OTel：API、Worker、队列、沙盒、Judge。
- 指标：实验成功率、排队时间、沙盒启动、Judge 延迟/成本、错误率。
- 日志：结构化 JSON；请求 ID/实验 ID 贯穿。
- 告警：PagerDuty/Slack；P0 15 分钟响应。

### 7.3 SLO

| 指标 | 目标 | 告警 |
|---|---|---|
| API 可用性 | 99.9% | 5xx > 1% 5min |
| 实验排队 p95 | < 30s | > 2min 10min |
| 实验成功率 | > 99% | < 97% 15min |
| 沙盒启动 p95 | < 10s | > 30s 10min |
| Judge 错误率 | < 1% | > 3% 10min |

### 7.4 备份与恢复

- Postgres 每日全量 + WAL；RPO 15min，RTO 1h。
- S3 版本化；报告/证据包保留 1 年。
- 每季度恢复演练。

## 8. 风险与缓解

| 风险 | 触发信号 | 缓解 | 负责人 |
|---|---|---|---|
| 评委不可信 | Kappa < 0.7 | 确定性优先、人工复核、缩小适用范围 | 评测 |
| 沙盒逃逸/泄露 | 安全扫描告警 | gVisor、网络拒绝、渗透测试 | 执行 |
| 成本失控 | 单实验成本 > 预算 2x | 级联、缓存、采样、配额 | 平台 |
| 设计伙伴不投入 | 连续 3 周无反馈 | 换伙伴、缩小场景、付费激励 | 产品 |
| 范围膨胀 | 里程碑延期 > 2 周 | 砍非核心功能、冻结新需求 | 研发 |
| 迁移丢数据 | 校验失败 | 备份、双写、回滚 | 平台 |
| 关键人依赖 | 单点 | 文档、结对、代码评审 | 全员 |
| 合规延迟 | 认证未过 | 提前法务/安全评审 | 产品 |

## 9. 资源与预算（量级）

> 以下为规划量级，不是财务承诺；按实际云/模型价格调整。

| 项 | 月成本（早期） | 说明 |
|---|---:|---|
| 基础设施 | $500–2,000 | 3 环境、Postgres/Redis/S3、K8s 小集群 |
| 模型调用 | $1,000–5,000 | 设计伙伴评测 + 校准；按用量增长 |
| 沙盒 | $300–1,500 | Docker/K8s；高敏客户 gVisor |
| 工具/监控 | $200–500 | OTel/日志/告警 |
| 认证/合规 | 一次性 $20k–60k | SOC2/ISO27001/等保，按范围 |
| 人力 | 5 FTE | 最大成本项 |

### 9.1 成本控制

- 每个实验设置 Token/美元预算；超预算熔断。
- Judge 缓存 + 小模型初筛。
- 沙盒池化与镜像缓存。
- 非生产环境使用低配模型。

## 10. 完成定义（DoD）

一个功能算"完成"，必须满足：

- [ ] 有明确的用户故事与验收标准。
- [ ] 代码通过 lint/type/test。
- [ ] 有单元测试 + 至少一个集成/E2E 覆盖。
- [ ] API 有 OpenAPI 文档；SDK 已更新。
- [ ] 有审计/权限/租户隔离（如适用）。
- [ ] 有错误处理、超时、重试、幂等。
- [ ] 有指标/日志/告警（如适用）。
- [ ] 文档更新（docs/ 与 README）。
- [ ] 设计伙伴或内部用户验收。
- [ ] 不引入未使用的依赖或死代码。

## 11. 周会与决策机制

- **周一计划**：本周目标、依赖、风险。
- **周三同步**：阻塞与跨组协调。
- **周五 demo**：可运行结果 + 指标。
- **决策记录**：重大变更写 ADR；产品范围变更由产品负责人拍板。
- **冻结期**：每个里程碑最后 3 天冻结新需求，只修 bug。

## 12. 第一周立即行动清单

1. 删除旧文档与临时产物；统一 `docs/`。
2. 重写 README（事实版）。
3. 建 issue 看板：P0（评委/评分/安全否决/队列）、P1（沙盒/双控/CI）、P2（在线/企业）。
4. 选定 3 个设计伙伴候选，发出共创邀请。
5. 收集 100 条人工标签（可从现有 benchmark + 设计伙伴样本）。
6. 冻结新 UI 功能，直到 M1 退出。
