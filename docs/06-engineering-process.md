# 06 · 标准研发流程

> 版本：1.0  
> 更新：2026-10-17  
> 状态：有效  
> 适用：AgentTestHub 所有功能、修复与重构

---

## 1. 原则

1. **问题先于方案**：先写清楚用户问题、证据、成功指标，再谈技术。
2. **小步提交**：一个 PR 只解决一个可验证的问题；大重构拆成可合并的步骤。
3. **测试与实现同 PR**：没有测试/验收标准的改动不算完成。
4. **文档与代码同源**：接口、数据模型、评测语义变更必须更新 `docs/`。
5. **可信度优先**：评测结论、分数、门禁必须可复现、可追溯、可校准。
6. **默认安全与私有化**：任何功能先问"能否在客户环境独立运行"。

---

## 2. 全流程

```text
问题定义 → 方案设计 → 任务拆解 → 实现 → 自测 → 代码评审 → 集成验证 → 发布 → 运营复盘
   RFC        ADR/UI Spec   Issues     PR      Tests     Review      Staging     Release   Postmortem
```

### 2.1 问题定义（RFC）

产出：`docs/rfc/YYYY-MM-DD-<topic>.md`（或 issue 模板）。

必须包含：

- 背景与用户问题（谁、什么场景、多痛、证据）。
- 目标与非目标。
- 成功指标（可量化，如 Kappa、false pass、耗时、采用率）。
- 约束（安全、合规、成本、兼容性）。
- 备选方案与推荐。
- 风险与回滚。

**Gate**：没有明确成功指标与验收标准的 RFC，不进入设计。

### 2.2 方案设计

按改动类型选择：

| 类型 | 产出 | 评审人 |
|---|---|---|
| 架构/数据模型 | ADR（写入 `docs/01-architecture.md`） | 架构组 + 后端 |
| API/契约 | OpenAPI 变更 + 兼容性说明 | 后端 + SDK/前端 |
| 评测语义 | Rubric/Evaluator 变更说明 + 校准计划 | 评测科学家 |
| 前端/交互 | 页面流程 + 设计稿/组件说明 | 设计 + 前端 + 产品 |
| 安全/合规 | 威胁建模 + 控制措施 | 安全 + 架构 |

**Gate**：涉及数据模型/API 破坏性变更时，必须先有迁移方案。

### 2.3 任务拆解

- 每个 Epic 拆成 ≤ 3 天的任务；超过 3 天继续拆。
- 每个任务写：输入、输出、验收标准、依赖、测试点。
- 使用 `docs/05-development-checklist.md` 的编号（如 `E6-04`）。
- 明确 P0/P1/P2；P0 未完成不启动新 Epic。

### 2.4 实现

- **Trunk-based**：短分支（≤ 3 天），频繁 rebase；大功能用 feature flag。
- **提交信息**：`type(scope): summary`，例如 `feat(evaluators): add sql ast checker`。
- **PR 大小**：≤ 400 行有效 diff；超过则拆分。
- **代码风格**：Ruff、mypy、ESLint、Prettier、TypeScript strict。
- **禁止**：未使用的依赖/死代码、硬编码演示数据、静默吞异常、无证据的分数。

### 2.5 自测

提交 PR 前必须：

- [ ] 单元测试覆盖核心逻辑（新增/修改）。
- [ ] 至少一个集成或 E2E 覆盖用户路径。
- [ ] 手动验证：空状态、错误、加载、权限、移动端。
- [ ] 安全检查：密钥/租户/输入校验/日志脱敏。
- [ ] 性能检查：N+1、长列表、超时。
- [ ] 文档/CHANGELOG 更新。

### 2.6 代码评审

评审清单：

- **正确性**：边界、错误、并发、幂等、超时。
- **安全性**：鉴权、租户隔离、注入、密钥、沙盒。
- **可维护性**：命名、分层、依赖方向、重复代码。
- **可测试性**：依赖注入、确定性、无隐藏全局状态。
- **可观测性**：日志、指标、Trace、审计。
- **兼容性**：API/SDK/数据迁移。
- **诚实性**：没有夸大能力；"实验性"标注清楚。

规则：

- 至少 1 名同领域 reviewer；安全/数据模型变更需 2 名。
- 作者不合并自己的 PR（除紧急修复并事后补审）。
- 所有评论 resolved 后才能合并。

### 2.7 集成验证

- CI 必须全绿：lint、type、unit、integration、contract、build、security。
- Staging 部署 + 冒烟测试。
- 数据库迁移在 staging 先跑，验证正向/回滚。
- 前端关键路径 Playwright 通过。

### 2.8 发布

- **发布列车**：nightly → beta（每 2 周）→ public minor（每月）→ enterprise（每季度）。
- **灰度**：先内部/设计伙伴，再扩大。
- **回滚**：一键回滚镜像 + 数据库迁移回滚脚本；保留上一个稳定版本。
- **变更日志**：用户可感知的变化、迁移步骤、已知问题。
- **门禁**：发布前检查清单（见 `05-development-checklist.md`）。

### 2.9 运营与复盘

- 监控 SLO；P0 事故 15 分钟响应。
- 每次事故写 postmortem：时间线、根因、影响、修复、预防。
- 每月复盘：指标、设计伙伴反馈、路线图调整。
- 每季度做一次"评测的评测"：Judge 与人工一致性、false pass/fail、flaky、复现率。

## 3. 测试策略（分层）

| 层 | 目标 | 工具 | 何时跑 |
|---|---|---|---|
| 单元 | 领域/评分/统计/解析 | pytest | 每次 PR |
| 集成 | DB/队列/沙盒/OTel | testcontainers | 每次 PR |
| 契约 | OpenAPI/SDK/Webhook | Schemathesis | 每次 PR |
| E2E | 登录→资产→实验→报告→门禁 | Playwright | 每次 PR（核心）+ nightly |
| 黄金集 | Judge 与人工一致性 | pytest + calibration | 每次 PR |
| 失败注入 | 评委/沙盒/网络异常 | pytest + toxiproxy | nightly |
| 压测 | API/Worker/沙盒并发 | k6/Locust | 每周/发布前 |
| 安全 | 依赖/镜像/渗透 | Trivy/ZAP/外部 | 每月/发布前 |

### 3.1 测试数据

- 不使用真实客户数据；使用脱敏/合成数据。
- 黄金集与场景包版本化；变更需评审。
- 任何评测结果必须记录 `n`、随机种子、模型版本。

---

## 4. 分支与版本

- `main` 始终可发布。
- 分支：`feat/<topic>`、`fix/<topic>`、`refactor/<topic>`、`docs/<topic>`。
- 版本：语义化；`0.x` 允许破坏性变更但必须写迁移说明；`1.0` 后 API 稳定。
- 数据库迁移：Alembic，禁止运行时 DDL；破坏性迁移分两步（先兼容后删除）。

## 5. 角色与会议

| 角色 | 职责 |
|---|---|
| 产品/评测负责人 | 问题定义、优先级、验收、设计伙伴 |
| 架构/后端 | 架构、API、数据、性能、安全 |
| 执行/沙盒 | Runner、沙盒、模拟器、红队 |
| 前端/设计 | 信息架构、交互、组件、可访问性 |
| 评测科学家 | Rubric、Judge、校准、统计 |
| QA/DevOps | 测试策略、CI/CD、SLO、事故 |

会议：

- **周一计划（30m）**：目标、依赖、风险。
- **周三同步（15m）**：阻塞与跨组协调。
- **周五 Demo（45m）**：可运行结果 + 指标。
- **双周复盘（45m）**：交付、质量、设计伙伴反馈。
- **季度规划（半天）**：路线图、Gate、资源。

---

## 6. Definition of Done

- [ ] 验收标准全部满足。
- [ ] 测试（单元/集成/E2E）通过。
- [ ] 文档/CHANGELOG 更新。
- [ ] 安全/权限/租户/审计检查通过。
- [ ] 性能在预算内。
- [ ] 可观测性（日志/指标/Trace）就绪。
- [ ] 回滚方案明确。
- [ ] 设计伙伴或内部用户验收。

---

## 7. 反模式（禁止）

- 用关键词/硬编码冒充评测。
- 用单次运行/单个分数对外宣称能力。
- 未接线的指标写进 README。
- 用"大厂实践/全球首个/95%"等不可验证背书。
- 巨型 PR、巨型页面、巨型函数。
- 静默失败、吞异常、无证据的 PASS。
- 为了 demo 牺牲安全/可复现性。
